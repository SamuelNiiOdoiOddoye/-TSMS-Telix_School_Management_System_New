# Telix School Management System — Documentation Library

Welcome to the official documentation library for the **Telix School Management System (TSMS)**.

This directory contains the documentation required to understand, operate, maintain, support and develop TSMS.

The documentation is organized into three main areas to ensure that readers can easily distinguish between the intended system, the currently implemented application and the instructions relevant to their responsibilities.

## 1. System Blueprint

**Location:** `01-system-blueprint/`

This section explains the complete intended TSMS platform.

It describes the system's vision, architecture, functional modules, business processes, security model, deployment structure, integrations and operational requirements.

It serves as the primary reference for understanding how TSMS is intended to work, including functionality that has not yet been implemented.

## 2. Current System

**Location:** `02-current-system/`

This section documents the actual TSMS application as it exists in the codebase.

It covers the implemented architecture, available functionality, application structure, database and storage arrangements, authentication, installation, configuration, testing and known limitations.

It must accurately reflect the current implementation rather than future plans.

## 3. User and Administration Guides

**Location:** `03-guides/`

This section contains practical instructions organized according to the people who interact with TSMS.

### School Users

`03-guides/01-school-users/`

Guides for teachers, students, finance officers and other authorized school personnel using TSMS.

### School IT Administrators

`03-guides/02-school-it-administrators/`

Guides for personnel responsible for installing, configuring, managing and maintaining their school's TSMS installation.

### Telix Team

`03-guides/03-telix-team/`

Internal operational and technical documentation for Telix administrators, engineers, support personnel and other authorized team members.

## Understanding Documentation Status

To prevent confusion between planned functionality and existing capabilities, documentation uses the following status descriptions:

| Status              | Meaning                                                                     |
| ------------------- | --------------------------------------------------------------------------- |
| Planned             | Intended functionality that has not been implemented                        |
| In Development      | Currently being developed                                                   |
| Partially Available | Some functionality exists, but implementation is incomplete                 |
| Implemented         | Functionality exists in the application                                     |
| Verified            | Functionality has been tested and confirmed against its acceptance criteria |
| Deprecated          | Functionality is no longer recommended or supported                         |

## Documentation Standards

All documentation should:

- Use clear, consistent and understandable language.
- Explain processes in a logical sequence.
- Distinguish intended functionality from existing functionality.
- Identify relevant user roles and responsibilities.
- Include diagrams, examples and screenshots where useful.
- Avoid exposing passwords, secrets or confidential school information.
- Be updated when the system's behaviour or architecture changes.

## Documentation Maintenance

The System Blueprint describes the intended platform.

The Current System documents the actual implementation.

The User and Administration Guides explain how to interact with and operate the available functionality.

These three areas must remain consistent while preserving their distinct purposes.
